# Reusable notebook blocks

The notebook retains Tiptap JSON as its canonical page content. Layouts contain real block nodes, so moving a block does not create a separate copy of its data. This step does not add a generic database builder or change production.

## Responsibilities

- `apps/web/src/features/notebook/blockCatalog.ts` owns typed insertion definitions, factories, supported block containers, and layout validation shared by browser recovery.
- `layoutBlocks.ts` owns schema nodes, pure undoable layout operations, heading discovery, and transient tab navigation.
- `LayoutViews.tsx` owns React node views and accessible page controls. The editor registers these renderers alongside schema extensions; slash commands use catalog definitions.
- `blockDrop.ts`, `moveBlock.ts`, `blockActions.ts`, and `blockColors.ts` use the container contract rather than assuming every block is at the document root.
- `services/api/app/schemas/notebook.py` validates accepted node shapes and attributes before storage. Update and regenerate both OpenAPI contracts for schema changes.

To add a future block, provide its schema, catalog factory, renderer, validation, and export behavior. Data views should keep source identities and view settings in the block and read shared records through API adapters; they must not duplicate source records into each presentation.

## Initial blocks

Columns contain 2–5 `column` nodes with editable blocks. Desktop starts with equal widths. Dragging the gap between neighboring columns previews their relative widths and saves one undoable change on release. Arrow keys resize a focused divider; double-click resets its neighboring pair. Widths live in the columns node attrs as numeric weights; mobile stacks columns in document order. A subtle grip above each column reorders the entire column, including nested blocks and its width. Columns can also move between rows using the same grip. Their relative width is carried to the destination; its other widths scale proportionally to make room. Dropping near the top or bottom edge of a row shows a horizontal line and moves all blocks from the column above or below that row at full width, in their original order. Source rows shrink or unwrap when only one column remains. Moves into the column’s own descendants or full five-column rows are rejected. A vertical line previews the destination. Arrow keys on the grip reorder without a pointer, and Escape cancels a drag. Locked pages hide the dividers and grips. Dropping a block near the left or right edge of another creates a two-column row. Dropping beside a block in an existing row adds a column, up to five. Side drops show a vertical insertion line, retain the original block content, and are one undo step. Moving the last block out of a column removes that column. A row with only one remaining column unwraps into regular blocks, retaining their order and formatting. Cleanup affects only the dragged block’s source columns; unrelated empty layouts stay intact. Surviving widths retain their proportions. Cleanup and the move undo together. Increasing the count adds empty columns. Reducing it appends surplus content to the last retained column. Undo restores the exact original structure.

Tabs contain 1–12 `tabPanel` nodes. Each panel has a stable UUID and a name up to 80 characters. Users can add, rename, reorder, or remove a tab; removal keeps its content in a neighboring tab. Navigation is transient editor UI state, does not create a saved page version, and resets to the first tab on reload. Arrow keys and Home/End navigate the tab strip. Locked pages retain navigation while hiding modification controls.

The table-of-contents node derives its entries from ordinary headings and toggle headings, including headings in columns, collapsed toggles, and inactive tabs. Clicking an entry reveals its ancestors and scrolls to it. It does not persist a second outline or stale heading positions.

All layout nodes use existing page saving, recovery, history, duplication, Trash and JSON backups. Markdown export linearizes columns and includes every tab, including hidden content; a table of contents becomes a readable outline. Layout presentation itself remains represented by the full JSON backup.

No database migration is needed: these nodes are stored in the existing page JSON payload. The web editor and API must both support the node types before they are used in an environment.

## Multiple block dragging

Drag-select text across blocks, Shift-click block handles for a range, or Cmd/Ctrl-click handles to add or remove individual blocks. Selected blocks receive a blue tint and a count. Drag any selected handle to move the group in document order. Groups can move into or out of toggles, callouts, tabs and columns, and side drops put the whole group into one new column. Empty source columns clean up using the existing rules. Selection stays transient and never enters page JSON. Escape or a plain content click clears it. The move, cleanup and selection mapping happen in one undoable transaction.

## Premade data views

`viewBlock` is an atomic block with a reusable renderer and saved `view`, `source`, `title`, `query`, `filter`, `sort`, `group`, `collectionId` and `metric` settings. The insertion catalog includes line, horizontal/vertical bar and number charts. Board, Calendar and Dashboard are fixed sidebar destinations; Table, Gallery and Feed are no longer insertable data views. Previously saved view nodes remain readable. Switch chart types in settings without copying records or creating a database. Views can sit inside columns, tabs, toggles and callouts and use normal block movement, duplication and history.

`viewModel.ts` owns record adapters, filter/sort/group operations, date boundaries and validation. `NotebookView.tsx` renders those records and shares source loading through a provider around the editor. Notebook pages resolve from current page state and link to the original page. Tasks read the existing TickTick status/import snapshot; meetings read Apple Calendar's status/import snapshot. Refresh reads the latest imported snapshot. Errors retain previously loaded records. These views do not import providers, complete tasks, change meeting events or create sample records. Source connection management remains in the planner.

The default source is an editable personal list. The existing page/task/meeting adapters remain optional read-only sources. No generic database builder is introduced. Charts count items or sum known numeric values in the selected groups; line charts use dated records. Legacy Calendar views honor exclusive end days for all-day events and report undated items. Card/list/table rendering is bounded to 200 visible records and charts to 30 groups; filters apply before those display limits. All records remain in their original source. Locked pages prevent saved view configuration changes; calendar navigation remains available. Markdown exports personal list records, including unattached lists owned by that page; imported-source views export their configuration. JSON backups preserve list data and view configuration without copying imported snapshots. No database migration is required. The API and browser recovery validate configurations before accepting them.

### Personal items and shared lists

Personal lists are stored once in the owning page's optional `lists` metadata. Each has a UUID, name and up to 1,000 items. Items have a UUID, title, status, optional date, optional non-negative numeric value, description and optional HTTPS image link. A page can own up to 50 lists. A view's `collectionId` references a list rather than duplicating it, so multiple views and pages show the same updates. A missing/trashed source stays a visible broken reference until its page is restored or another list is chosen.

The item dialog saves or cancels explicitly; deletion offers Undo. List mutations use the existing notebook revision/conflict journal and page version history. Page locks protect both content and owned lists on the client and API. View layout edits use editor undo; item edits are page metadata and can be recovered through page history. Duplicating a page makes independent copies of its owned lists and remaps views targeting those lists. References to external lists remain shared. Existing PostgreSQL JSON payloads already store the complete page, so no database migration is required. Both contracts include the typed personal-list schema. Chart metrics can count items or sum known values; unknown values stay unknown, and an all-unknown sum displays a dash.

Status boards for personal lists start with To do, In progress and Done and keep empty destinations visible. Drag a card between them to update its canonical item status; shared views update from the same list. Focus a card and use Alt+Left/Right as a keyboard alternative, or edit its status in the item dialog. Day-grouped and imported-source boards remain read-only for dragging. Both the viewing page and source-page locks disable card moves. Dragging changes only status, retaining dates, values and other item fields.

Board cards can be dropped above or below another card to save a manual order in the canonical list item array. A card move switches that view to Manual order; Name/Date sorting remains available. New boards default to manual order. Filtering retains relative manual order and moves preserve hidden items. Alt+Up/Down and the card arrow buttons reorder without dragging. Cross-column drops can also choose a precise position. Ordering shares existing page metadata persistence and source-page locking.

## Fixed pages, clean charts and image grids

Tasks, Meds and Dashboard are singleton page destinations created on first open, stored with typed `kind` metadata and one matching `viewBlock` in their content. Sidebar navigation reuses the saved page, including after reload. They have no body editor, slash insertion or normal page actions. The Board supports its normal editable title, icon and cover; Meds and Dashboard retain fixed headings. Their lists, view settings, recovery and backups use the existing notebook store. Recovery copies become ordinary pages to keep the fixed destinations unique. Meds uses the Dashboard renderer without a cover.

Chart blocks show a title, chart, Edit data action and settings icon. Source/filter/group/sort/type controls live in a settings dialog; search is removed from the chart surface. Edit data opens a compact table with names, values, dates and statuses, explicit Save/Cancel, and add/remove rows. New chart data is saved as a canonical list with Sum values selected. Bars group by item name by default; line charts use dates. Existing shared lists can be selected in settings. Cell changes merge into current items without overwriting unrelated newer fields or resurrecting rows deleted elsewhere.

`imageGrid` is an atomic layout block with 2, 3 or 4 image slots (4 uses two-by-two). Each slot accepts an uploaded image through the existing authenticated image endpoint or an HTTP(S) link, with alt text. Replace and Remove retain the grid layout. Locked pages disable controls. Grid attrs are validated by browser recovery and the API, retained in full JSON backups, and exported as individual Markdown images. No database migration or dependency addition is required.

The fixed Board page supports the normal editable page title, page icon and cover picker/repositioning. Its + New item action is available before a list exists; saving the first card creates and selects a Board items list on that page. Cancelling leaves no empty list. Later cards use the same list. Board content remains a dedicated view rather than an editable document body.

The fixed Board settings expose only filtering, order and grouping. Its backing source/list stays connected internally; source selection, list management and the redundant view title are hidden. The page title remains editable above the board, and + New item continues to use its existing list. Other chart and fixed-page settings are unaffected.

Page and callout icon pickers share a 104-icon SVG catalog in `pageSymbols.ts`, alongside the existing emoji choices. Browser recovery uses that catalog for stored icon validation; the API exposes the same allowlist in both OpenAPI contracts. Existing icon IDs remain stable. Search, keyboard navigation, removal and page-lock behavior are unchanged.

The picker includes space, mind and fire variations (planets, UFO, astronaut, galaxies, neurons, thought bubble, campfire, torch and candle), plus 70 emoji presets. Search matches their descriptive names.

Status boards use neutral gray, blue and green tinted columns and dotted pill badges. Each editable status column offers New task with inline name entry; Enter/Add task saves to that status and Escape/Cancel leaves no item. The header action is also named New task. Source-page and viewing-page locks hide both creation controls. Existing status IDs and saved card data are unchanged.

Each status column has a Column settings menu for a display name (up to 60 characters) and one of nine colors. The canonical personal list owns its board column definitions and order, so shared views use the same names and colors. Existing view-level overrides are retained as a fallback and adopted into the list on its first column edit. Built-in status IDs retain their completion semantics; custom column UUIDs represent open tasks. The task editor uses the displayed column names. Save commits both fields; Cancel/Escape leaves them unchanged. Browser recovery and the API validate the configuration. JSON backups and duplication retain it.

Use Add column at the right edge of a status board to create a named, colored column. Boards support 1–20 columns. Column settings offers Delete column; deleting an occupied column requires choosing another column and moves every task, including filtered tasks, in the same saved list update. Empty columns can be deleted directly. The final column cannot be deleted. Locks disable column changes. The typed list board definition and task assignments are validated together by the browser and API, retained in backups, duplication and page history, and stored in the existing PostgreSQL JSON payload without a migration.

The board header three-dot control opens a compact group menu with Edit group (name/color), Hide/Show aggregation (item counts for this view), Hide group, and Delete group. Hidden groups remain listed below the board with a Show control and retain their tasks and statuses. `hiddenColumns` and `hideAggregation` are view preferences, independent of the canonical shared list. They survive reloads, backups and duplication; hidden-column IDs may remain inert after a column is deleted. Keyboard arrows/Home/End navigate the menu, Escape/outside click dismisses it, and deleting still requires task reassignment. Locked boards prevent these saved changes.

Drag a status column by its name/count header to reorder the whole column. A vertical blue insertion line previews before/after placement; dragging near the board edges scrolls it horizontally. Column dragging uses a separate drag type from cards and never reassigns or reorders items. Alt+Left/Right on the header and Move left/right in its menu are alternatives. Hidden columns retain their relative order. Moves update the canonical `list.board.order` using the existing revision/history/lock path and persist across shared views and reloads; no schema migration or dependency is needed.

Board task details open as an animated, full-height right panel (full width on phones). Valid edits autosave immediately into the existing notebook journal and revision-checked server queue. Escape, the close arrow or clicking the backdrop closes the panel while preserving saved changes. The toolbar shows the actual notebook save status and exposes retry for errors; no task Save/Cancel footer remains. Invalid field drafts are retained in the panel until corrected or explicitly discarded, while valid changes to other fields continue saving. New empty panels create nothing until the first valid edit. Field patches merge into the latest item and cannot recreate a task removed elsewhere. Focus returns to the opener, the native dialog traps focus, and reduced-motion preferences disable sliding. New tasks use the same panel; other item editors retain their modal and explicit Save/Cancel flow. Task status choices follow the canonical board columns, including custom columns. Done tasks have struck-through titles in record cards/links and in the panel; moving them to an open status removes the styling. No persistence format or API change is required.

Task side panels resize from their left edge on desktop. Width is bounded to 400–1,100 px while retaining at least 240 px of the background; the preferred width is stored only in this browser, independently of task data. Left/Right arrows resize by 20 px, Home/End select the limits, and double-click resets to 720 px. Narrow panels use compact property spacing; phones stay full width and hide the resize handle. Pointer capture keeps resizing reliable when the cursor leaves the edge.

Task property rows share one value column and use SVG type icons. Status opens a colored choice menu; Date opens an inline calendar with month navigation, a YYYY-MM-DD entry field, Today and Clear date, without a native date-input icon. Day buttons support arrow keys/Home/End; Escape closes the picker before the task panel. Popovers stay within the viewport.

Add a property creates a typed definition on the canonical personal list, shared across its tasks/views. Up to 30 properties support 16 active types: Text, Number (signed values), Select, Multi-select, Status, Date, Files & media, Checkbox, URL, Email, Formula, Rollup, Created time, Last edited time, Button and ID. Definitions have stable UUIDs, names up to 60 characters and up to 30 choices; task values are stored by property UUID. Editing a property name preserves values. Used choices cannot be removed until their values are cleared; existing types can change through the Type selector in the property editor. Conversion previews cover the entire canonical list, including filtered-out tasks. Numeric text, unambiguous checkbox/date values, single/multiple choices, file links and existing task relations convert when valid. Selection choices are inferred up to the existing 30-choice limit. Multi-select values with more than one choice are not silently reduced to one choice. Calculated fields become editable snapshots when converted to manual types; converting to automatic types clears stored manual values. Incompatible values are shown in a preview and require a second explicit confirmation. Approval is tied to the actual affected values/settings, so a stale approval cannot silently clear newly changed data. Definition and values update atomically under the same property UUID; prior values remain in page history. Retired Person, Phone, Created by, Last edited by, Place and Relation types cannot be selected or newly created; stored definitions still validate for compatibility and can be converted to active types. Deleting a property requires a second explicit action and atomically removes its values from all tasks; page history retains the earlier state. Formula uses a bounded interpreter, never JavaScript evaluation: `prop("Name")`, arithmetic/comparison/boolean operators and if/empty/round/floor/ceil/abs/sum/min/max/concat/length. It is a local subset, not Notion's complete formula language; missing dependencies and cycles display errors. Relations select up to 30 tasks in a personal list; rollups count or calculate sum/average/min/max/unique values over that relation. Deleted targets remain visible as unavailable links until cleared. Renaming formula dependencies requires updating the formula. Duplicated/recovered pages remap relation list ownership. Computed values are derived on display/export and cannot be stored as editable values.

Legacy Person values remain readable in this private, single-owner workspace. Created/edited metadata records You and ISO timestamps; legacy creation times are recovered from the earliest available saved page history, without claiming a date before that record; missing history remains Unknown. The read-only task-metadata endpoint recovers timestamps independently of page-only changes. Metadata hydration does not count as a task edit. Last edited metadata tracks task edits and status changes, while pure card reordering retains timestamps. ID uses a permanent positive sequential number per canonical list, with an optional prefix (default TASK). A retained idCounter prevents number reuse after deletion; reordering and editing never change a task's number. Prefix changes affect display only; click an ID to copy it. Legacy Place values remain readable as address text. Status is an independent single-choice task property; the built-in board Status still determines column placement and completion. Buttons support a configurable label, up to ten ordered actions, and an optional confirmation. Actions edit built-in or custom writable fields, mark done, move to the To-do group, set today, or check a chosen checkbox. Every action is validated before a single atomic task patch; renamed Complete/To-do groups work by group identity. They do not run arbitrary scripts or external actions.

Files & media accepts HTTP(S) file links or uploads up to 8 MB each (30 per value). Immutable attachment bytes live in `notebook_attachments`, introduced by local Alembic migration 0005; database dumps include them. Uploads are streamed with a hard limit; downloads use authenticated same-origin routes, octet-stream, attachment disposition, no-sniff and a sandbox CSP. Unlike cover images, file bytes are preserved. JSON export references the stored assets; a standalone JSON backup does not include binary files. Connected-service properties and AI Autofill are outside this scope. Property edits and values follow existing autosave, source locks, revision conflicts and recovery. Browser/API validation rejects orphaned or mismatched values. Duplication, JSON backups and Markdown exports preserve properties. The existing PostgreSQL JSON payload stores them without a migration; both OpenAPI exports include their schema.

The Add a property popup follows the Notion name-first flow: an optional property name above the Type section, a Search types button, and a plain keyboard-navigable type list. Selecting a type immediately creates it and focuses its value; there is no separate Create property action. Blank names get unique type-based defaults. Select/Multi-select definitions may initially have no options. Their value popup searches existing options or creates and selects a new one; definition and value changes save in one canonical list update. Existing values survive adding choices.


Property settings use a compact icon/name header and a custom searchable Type menu with keyboard navigation and a current-type checkmark. Names save on Enter or blur; no permanent Save property footer is shown. Options are individual pill rows with add, rename and delete controls instead of a bulk textarea. Renaming an option updates all existing task values atomically; deleting a used option requires explicit review and removes only that choice from multi-select values. Duplicate property creates a fresh property UUID, a unique copy name, independent choices/configuration and copies values for every task. Type conversion keeps its existing preview/confirmation; advanced configuration shows Apply changes only while settings differ. The removed property types remain absent from selection. Menus preserve the system font and adapt to narrow screens; native popover Escape/backdrop behavior remains.


The built-in task Image property opens an Upload/Link popover instead of editing a raw URL in place. Uploads reuse normalized notebook cover assets (JPEG/PNG/WebP/GIF, 8 MB). Link insertion validates the HTTPS URL, rejects embedded credentials and checks that the browser can load an image before replacing the current value. Same-origin stored-image links normalize to their asset path. The popover shows a preview and Remove image; board cards render the saved image as a clickable thumbnail opening that task. Failed links retain the prior image, broken saved images show an explicit fallback, and closing the popover cancels pending uploads/loading. Images use the existing task `cover` field and autosave/revision/history flow; no API migration is required.

Select and multi-select value menus use a selected-tag composer above a searchable option list. Remove tags with their × button or Backspace in an empty search; use Up/Down and Enter to choose or create an option. Single-select closes after choosing; multi-select stays open. Creating a choice and selecting it save together.

### Rich task notes

The task side panel uses the shared `PageEditor` Tiptap component for its body, including slash commands, selection formatting, block actions, lists/checklists, toggles, callouts, tables and image upload/link insertion. Page creation and data-view insertion are omitted from task notes. `PersonalItem.descriptionContent` stores the optional rich document; `description` remains a plain text summary (up to 5,000 characters) for existing views and search. Existing descriptions become literal paragraphs only when editing; opening a task never rewrites old notes or interprets Markdown-like characters. Rich notes autosave atomically with their summary and are retained in notebook history, browser recovery, duplication and backups. The API validates the rich body with the same bounded document validation as page contents (1 MB, depth 40, 20,000 nodes). Locked tasks remain read-only. No database migration is needed because items live within the existing page JSON; a future hosted release must include the matching API schema before the web UI.

### Property-name actions and visibility

Clicking a custom task property name opens Rename, Edit property, Property visibility, Duplicate property, Delete property and Customize layout. Edit property opens the existing type/option editor and preserves type-conversion review. Visibility supports Always show, Hide when empty and Always hide, shared by tasks on the board. Hidden fields retain their values; Add a property → Customize layout restores them. Automatic/calculated fields use their displayed value when deciding whether they are empty; zero and false remain populated values. Deleting a custom property removes its display settings as well as its definition and values, with history retaining previous versions.

The built-in Value label also opens property actions. Its label and visibility are configurable; Duplicate property copies each task's number into an independent custom Number property, which can then change type. Its built-in type remains Number because chart metrics use that field. The optional `PersonalList.propertyDisplay` map persists these preferences (custom UUID keys or `value`, up to 31 entries); old lists default to visible fields. Preferences are validated by the API and included in history, lock protection, recovery and backups. No database migration is needed. This remains a local change and requires the matching API schema in any future hosted release.

### Number property presentation

Custom Number properties and built-in Value support Edit property → Show as Number, Bar or Ring. Bar/Ring options include the notebook color palette, a positive finite Divide by (up to 1 trillion) and Show number. These settings autosave in the property's `propertyDisplay[id].number` record and apply across tasks; built-in Value also passes its presentation to existing table renderers. Numbers remain numeric and unchanged for formulas, rollups and chart aggregates. Progress uses `value / divideBy`, clamped to 0–100% for drawing only; the raw value stays intact (including negative numbers and values above the divisor). Null remains Empty; zero renders zero progress. Bar/ring values remain clickable/editable even with their visible number hidden. Invalid divisors retain the last valid setting and show an error. Duplication copies presentation into an independent settings object. API validation, revision no-op normalization, locked-page protection, history and backups retain these settings. New API schemas must ship with any future requested hosted release; this work is local.

Numeric value editing uses a single input with no Clear/Done action rows. Valid numbers autosave as typed; deleting the contents saves an empty value. Enter dismisses the editor, and blur/light dismissal closes it without stealing focus from the next field. Invalid drafts retain the last valid saved number.

Select and Multi-select use colored tags in task properties. Options can be searched or created from the value picker, edited through each row's ellipsis, and reordered by dragging (or Move up/Move down). The property editor also offers Manual, Alphabetical, and Reverse alphabetical presentation sorting. Color and sort preferences live in the property's config (`optionColors`, keyed by canonical option name, and `optionSort`); existing string values remain compatible. Renaming/deleting an option updates its colors and all affected task values atomically. Duplicating a property copies colors independently. Used-option deletion retains an explicit confirmation, and previous values remain in page history.

Select option settings open in an anchored nested popover, retaining the parent list. Tags use a separate dark-mode Select palette sampled from the Notion reference, including Default (removing an explicit color). Add an option opens a top-of-list input; Enter creates the option and keeps the input ready for another. Visible scrollbars are hidden only on Select option surfaces; wheel, touch and keyboard scrolling remain available. Alt+Up/Down reorders focused option rows.

Multi-select uses the same option palette, inline creation, sorting and anchored color/rename/delete menus as Select. Its selected tags wrap inside the picker and remain visible on the task property. Choosing or creating tags keeps the picker open; clicking a selected option toggles it off, and each selected chip has an individual remove control. With an empty search input, Left enters the selected chips, Left/Right moves between them, and Delete/Backspace removes a focused chip. Input composition does not accidentally create or select an option.

Status properties use fixed semantic groups (To-do, In progress, Complete), grouped value pickers, rounded colored dot pills, and a grouped options editor. Options can be added within each group, dragged between groups, renamed, recolored (including Default), deleted, or chosen as the default for new tasks. Canonical option strings remain stable on group/color changes. Status metadata lives in `PropertyConfig.statusGroups` and `defaultStatus`; deleting/renaming options updates these references atomically. New Status properties initialize existing tasks to their default, and new task creation initializes custom Status defaults.

The built-in board Status picker also uses the three groups. A board column's optional `group` is configured alongside its name and color in Column settings. Complete membership controls task/board completion styling and dashboard open/done calculations; legacy To do/In progress/Done IDs retain their previous meaning without migrating data. Column IDs and task assignments are unchanged by group changes. These fields remain in existing page JSON; no database migration is required.

Files & media properties display attachment names and thumbnails instead of a count. Their compact popover has Upload/Link tabs, multiple-file and folder selection (flattened into attachments), drag/drop and image paste. Raster attachments have a bounded, metadata-stripped WebP preview at `/api/notebook/attachments/{key}/{filename}/preview`; original downloads remain byte-for-byte attachments. SVG, HTML and invalid rasters cannot be served as inline previews. Images open in a preview dialog; other attachments open/download through the original file URL. Relation is retired from Add a property and Change type, and cannot be newly duplicated or converted into. Legacy definitions/values remain valid for older notebook snapshots, history, backups, and conversion to another supported type. Existing Rollup fields are retained.

Task system fields and Button automation settings are stored in existing page JSON, included in backups and both OpenAPI exports; no database migration is needed.
