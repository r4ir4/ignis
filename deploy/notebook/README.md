# Hosted notebook: staging and production preparation

`notebook_main.py` is the hosted API entry point. It exposes notebook, native Habits and Meds routes and a private readiness check; local provider integrations, Markdown Notes and Watch are not included in its image. The gateway forwards only `/api/notebook`, `/api/habits` and `/api/meds` to this authenticated API.

Every notebook request independently revalidates its session cookie against the existing internal Ignis Tinyauth service. Only its verified `Remote-Email` can match `IGNIS_NOTEBOOK_OWNER_EMAIL`; browser-supplied identity and forwarding headers are ignored. Canonical Host and exact Origin on writes are required. Authentication outages fail closed. HTTPS and the existing forward-auth middleware also protect the staging frontend. The existing auth.env and authentication volume are never copied or modified.

## Separate stacks

- Staging: `/opt/ignis/notebook/staging/`, `https://staging.ignis.farm`.
- Production preparation: `/opt/ignis/notebook/production/`. API and database are private; the production frontend/router is disabled behind the `release` profile.
- Dedicated PostgreSQL 18.6 clusters, Docker volumes, internal database networks, passwords and backup directories per environment. No host database/API port is published. Raira and Watch databases are independent.
- API runs as UID 10001 with a read-only filesystem and a private `/data` bind mount. The application database role cannot create roles or databases and is not a superuser. Alembic runs as a one-shot dependency before API readiness.
- Server-only `runtime.env` and `postgres.env` are generated by `provision_secrets.py` with mode 0600 and never printed. Keep them on the server and in protected infrastructure backups. Rerunning does not rotate existing database credentials; the explicitly supplied `--owner` updates owner authorization. Current owner: `rairarocks@gmail.com`.

The image is built from a deliberately small context: `requirements.txt`, `alembic.ini`, `migrations/`, and only `app/notebook_main.py`, `app/notebook_backup_worker.py`, plus the notebook route/db/model/schema/service/backup modules at their existing paths. Copy the Dockerfile and `.dockerignore` into that context. Exclude macOS AppleDouble files and Python caches; Alembic treats AppleDouble `.py` files as migrations otherwise.

Run `ssh cabecao python3 - --owner rairarocks@gmail.com < deploy/notebook/provision_secrets.py` to configure credentials on the host.

Render compose with `python3 deploy/notebook/render_stack.py staging` or `production`, saving the result as the appropriate server `compose.json`. Copy `init-db.sh`, `nginx.conf` and a rendered `notebook-proxy.conf` into that stack directory. Replace `http://api:8000` with the explicit `http://ignis-notebook-staging-api:8000` or `http://ignis-notebook-production-api:8000`; generic `api` aliases collide on the shared auth/proxy network. Copy the Node 24 web build only to staging `public/` at this stage.

Prepare each `/data` bind directory owned by UID/GID 10001 with mode 0700. Then run on the host:

```sh
docker compose -f /opt/ignis/notebook/staging/compose.json up -d
docker compose -f /opt/ignis/notebook/production/compose.json up -d api backup
```

Do not enable the production `release` profile while the old `ignis-site-1` still owns the same Traefik hostname. Production routing/cutover requires a reviewed release plan and a backup of the current static site/configuration. Provisioning this stack does not migrate browser or localhost pages and does not replace the live frontend.

## Backups and restore

A separate worker attempts the daily PostgreSQL dump at startup and retries hourly, including while no browser is open. Successful API writes also attempt the daily dump. At most one successful UTC-day snapshot is kept per day; this is daily recovery, not point-in-time recovery of every edit. Files live under the environment's `data/backups/`, mode 0600, with private uniquely named partial files and no automatic pruning. Backup failures are recorded in `backup-error.txt` and logs. Check both file age and errors when operating the service.

A dump on this VPS does not protect against losing the VPS. Recurring off-host copies now pull fresh staging and production snapshots to the explicitly selected Mac every six hours while it is awake, signed in and online. See the off-host operations section below. Credentials are excluded from these archives and ordinary release bundles.

`verify_database.py` runs on the host: it verifies role restrictions, absent database host ports and migration state, then dumps staging and restores into a new randomly named disposable database. It uses application-role dump credentials, retains a private checkpoint in staging `verified-backups/`, and compares all page payloads (including formatting), history and revision before dropping only that generated test database. It never restores over either real notebook.

```sh
ssh cabecao python3 - < deploy/notebook/verify_database.py
```

Production was initially provisioned empty; it now contains the preserved user notebook after the completed release. Staging fixtures remain separate. The HTTPS owner session, UI saves/reloads, history/Trash, anonymous rejection and off-host production restoration have been verified; see `docs/notebook-production-release.md`.

The 17 October staging result and remaining release checks are recorded in `docs/notebook-staging-validation.md`. Earlier manual checkpoint copies are retained alongside the new independent recurring backup destination.


## Recurring off-host backups to this Mac

Selected by the user on 17 October 2026. The application, auth service, staging and prepared production databases stay on the VPS. The `127.0.0.1:5173` preview and its development database are separate Mac services; they are not the hosted notebook.

- VPS exporter: `/opt/ignis/notebook/scripts/export_backup.py`. Each invocation makes fresh PostgreSQL custom archives from both notebook APIs' restricted application credentials. It streams those archives and a SHA-256 manifest over existing SSH and removes its own temporary files. It does not export database passwords, auth.env, authentication databases, Watch or Raira data.
- Mac LaunchAgent: `~/Library/LaunchAgents/farm.ignis.notebook.offhost-backup.plist`, user job `farm.ignis.notebook.offhost-backup`. It runs immediately when loaded and every 21,600 seconds while the Mac is awake and the user session is available. It does not wake the computer. Existing SSH access must remain available without a password prompt; interactive authentication failures are logged for the next attempt.
- Installed client and logs: `~/Library/Application Support/Ignis/notebook/offhost/`. Completed snapshots: `snapshots/<UTC timestamp>/`, each containing `staging.dump`, `production.dump` and `manifest.json`. Directory permissions are 0700 and files 0600. No automatic deletion or pruning is configured.
- Transport enforces existing SSH host-key verification. The client validates exact archive member names, PostgreSQL archive signatures, byte lengths and SHA-256 values, then atomically publishes the completed snapshot. Failed or partial transfers leave earlier snapshots untouched. Concurrent invocations are serialized.
- `snapshots/status.json` records the last attempt, last success, completed snapshot and failure status. `backup.log` and `backup-error.log` record task output. These are local operational records, not a notification service. No automatic stale-backup alert is installed.

The first real LaunchAgent run completed successfully. Both downloaded archives were restored on this Mac into separately generated disposable databases, validating document/tree structure and recovering staging's 5 pages, 16 history entries and revision 13, plus production's empty migrated database. No application database was overwritten.

Install/update after explicitly selecting this Mac as the destination:

```sh
ssh cabecao 'mkdir -p /opt/ignis/notebook/scripts; chmod 700 /opt/ignis/notebook/scripts'
scp deploy/notebook/export_backup.py cabecao:/opt/ignis/notebook/scripts/export_backup.py
python3 deploy/notebook/install_mac_backups.py
```

The installer copies the standard-library-only client out of the checkout into the private runtime directory, so moving the project does not break backups. Python 3.11+ and the existing `cabecao` SSH alias are required. The current installed Python is the existing Python 3.13 framework installation; keep that runtime available.

Inspect or manually run the job:

```sh
launchctl print gui/$(id -u)/farm.ignis.notebook.offhost-backup
launchctl kickstart gui/$(id -u)/farm.ignis.notebook.offhost-backup
PYTHONPATH=services/api services/api/.venv/bin/python deploy/notebook/verify_offhost_restore.py
python3 -m unittest discover -s deploy/notebook/tests -q
```

The restore checker uses the dedicated local PostgreSQL cluster and only creates/removes random test databases. It needs that local cluster running. A replacement VPS restore should instead restore a chosen verified dump to a newly provisioned empty database and validate it before routing traffic; do not restore over a populated notebook.

The six-hour off-host interval is conditional on Mac availability; an asleep/offline Mac can leave the newest off-host recovery point older than six hours. Daily VPS dumps remain independent. This destination choice protects against VPS loss without adding another cloud account, but it is not an always-on remote backup service. [Apple's launchd reference](https://github.com/apple-oss-distributions/launchd/blob/main/man/launchd.plist.5) documents the job configuration.
